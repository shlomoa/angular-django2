## mapping between openui-spec and angular-django2.

See [OpenUI Specification Implementation Plan](openui-spec-implementation-plan.md) for the three-layer architectural roadmap bringing `angular-django2` to complete specification compliance using only spec-defined selectors.

synthetic nodes. See [`migrate_schematics_to_openui_plan.md`](https://github.com/shlomoa/angular-django2/blob/main/docs/migrate_schematics_to_openui_plan.md)

| :-------------------------------------------------------- | :------------------------------ | :------------------------------------- |
| `Form` (+ `TextInputs`, `RangeControl`, `ActionControls`) | `reactive-form`                 | Active                                 |
| `TextInputs`, `RangeControl`                              | `form-field`, `field-component` | Active                                 |
| `SurfaceContainers` (+ composed children by `[slot]`)     | `component`                     | Active                                 |
| `SurfaceContainers` card (+ `OverlayContainers`)          | `complex-component`             | Active                                 |
| `[slot]` placement of composed children                   | `embed-component` (`--slot`)    | Active                                 |

### 4. Naming Conventions in `openui-spec`: Plural vs. Singular IDs

In `openui-spec`, certain objects (such as `tables`, `charts`, `lists`, `tabs`, `expandablePanels`, `textInputs`, `choiceControls`) use plural identifiers, while others (such as `dialog`, `stepper`, `dataGrid`, `dashboard`) use singular identifiers. This distinction follows two architectural rules:

1. **Family-Level / Grouped Leaf Scopes (Plural)**:
   - Scopes that represent an entire **category or family of related components** use plural names:
     - **`charts`**: Groups a family of chart variations (bar, line, pie, area charts) rather than a single specific chart type.
     - **`lists`**: Groups collection representations (ordered, unordered, selectable item collections) following the `ul`/`li` collection model.
     - **`tables`**: Groups high-level tabular presentations that include sorting, filtering, and pagination behaviors.
     - **`Widgets/`**: `feedbackWidgets`, `mediaWidgets`, `navigationWidgets`, `menuWidgets`, `dateTimePickers`.
     - **`Containers/`**: `surfaceContainers`, `structuralContainers`, `expandablePanels`, `tabs`, `sheetContainers`, `overlayContainers`, `splitters`.
     - **`Controls/`**: `textInputs`, `choiceControls`, `rangeControls`, `pickerControls`, `actionControls`, `displayPrimitives`, `statusIndicators`, `linkAndScrollControls`.

2. **Singular / Discrete Component Scopes (Singular)**:
   - Scopes representing a single, specific interaction widget or layout use singular names:
     - **`dialog`**: A specific modal or non-modal overlay surface.
     - **`stepper`**: A specific sequential wizard process flow.
     - **`dataGrid`**: A specific interactive tabular data grid widget.
     - **`dashboard`**, **`shellPage`**, **`emptyPage`**: Specific page layouts.

3. **Architectural Analysis: The Issue of Disambiguation and Pluralization**:
   - In a truly **implementation-agnostic specification**, ambiguity is senseless. A Table is conceptually a **table**, not "tables". While the content, appearance, and behaviors (such as sorting, filtering, or pagination) of a table vary across usage, the core notion of a Table as a tabular data presentation is unique.
   - The existence in earlier `openui-spec` versions of both a primitive `table` (`Controls/Table/table.scope.md`) and a composite `tables` (`Widgets/tables.scope.md`) represented a design defect where HTML implementation details leaked into what should be an abstract specification.
   - **Resolution in `openui-spec`**: This architectural defect has been resolved. `Controls/Table/` was retired, and `Widgets/table.scope.md` established a single, unified, technology-independent `Table` specification (`id: table`). Column definitions, row models, and behaviors (`sort`, `filter`, `paginate`) are facets of that unique Table concept, and downstream generators and tooling (such as `angular-django2` when a table schematic is added) treat Table as a unified concept mapping directly to target framework implementations (such as Angular Material `mat-table` + `matSort` + `mat-paginator`).
